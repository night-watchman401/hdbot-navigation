# 平面 GNSS 多普勒后端

本软件包为现有的二维 `slam_toolbox` 前端添加了一个基于 GTSAM 的 `karto::ScanSolver` 插件。所有 Karto 相邻帧边和回环边都保留原有的相对位姿观测值，以及在源坐标系下定义的协方差。求解器采用加性平面相对位姿残差，而不是与原有协方差定义不兼容的 SE(2) Logmap 残差。此前，该工作空间中并不存在 GTSAM 后端。

## 构建

经过测试的依赖为 GTSAM 4.3.0 开发版本，提交哈希为 `71a25ca36c084cbad1f872e812d6d97fbadfdb05`。仅凭版本号不足以确认兼容性：CMake 会先编译并链接 GTSAM 官方提供的、适用于局部导航坐标系的 `DopplerFactorArm` 构造函数，验证通过后才接受该依赖。未修改任何 GTSAM 源代码。

完整依赖安装、固定版本 GTSAM 构建和模块构建命令见仓库根目录的 [安装说明](../../../docs/INSTALL.md)。GTSAM 是外部依赖，不随本项目分发。

## 运行

```bash
# 先启动你自己的机器人或仿真，提供激光、里程计、IMU 和 TF。
ros2 launch hdbot_gtsam_backend slam_gnss.launch.py
```

不要同时运行第二个地图构建节点，或运行其他会发布 `map -> odom` 变换的 AMCL 节点。原有的 Ceres 配置仍可使用；上述启动文件通过 `config/gnss_backend.yaml` 覆盖求解器选择。

GNSS 输入话题为 `/gnss/doppler`，消息类型为 `hdbot_gnss_msgs/msg/DopplerEpoch`。这是**原始数据接口**，不是 GNSS 驱动程序。系统还需要现有的 `/imu`、`/odom`、`/scan` 和 TF 数据。仅提供一条 `NavSatFix` 消息是不够的。

请复制 `config/gnss_backend.yaml`，在副本中配置以下内容，并通过 `gnss_params_file:=...` 传入该文件的绝对路径：

* `ecef_from_map_translation_m`：地图坐标系原点在 WGS84 ECEF（地心地固）坐标系下的位置。
* `ecef_from_map_quaternion_xyzw`：从 `map` 坐标轴旋转到 ECEF 坐标轴的旋转四元数。必须包含实际的 `map` 到 ENU（东—北—天）坐标系之间的对齐关系，不能假定 `map` 就是 ENU。
* `georeference_ready: true`：明确声明上述坐标变换已经完成标定。
* `lever_arm_body_m`：从车体原点（`base_footprint`）指向天线的杆臂向量，以车体坐标轴表示。机器人模型有意保持不变，需要由用户自行调整。
* `body_from_imu_quaternion_xyzw`、`gyro_bias_imu_radps`：IMU 到车体的旋转关系，以及标定后的陀螺仪零偏；使用测得的角速度之前会应用这些参数。
* 话题名称和坐标系名称须与实际消息一致。里程计的速度（twist）必须表示在配置的车体原点处，其 `child_frame_id` 必须与 `base_frame` 一致。

如果没有配置地理参考坐标变换，节点仍会优化原有位姿图，但**不会添加 GNSS 因子**。默认的零杆臂仅是占位值，不能提供直接的旋转信息；系统不会自动标定杆臂。

GNSS 消息时间戳必须事先转换到与其他传感器相同的 ROS 时钟基准。驱动程序必须提供：以 Hz 为单位、**接近时为正（positive-closing）**的多普勒观测值；以 m/cycle 为单位的波长；卫星在 ECEF 坐标系下的位置和速度；以 s/s 为单位的卫星钟漂；天线在 ECEF 坐标系下的标称位置；观测有效性标志；以及以 m/s 为单位的距离变化率标准差。卫星状态必须与观测所用的时间和改正模型约定一致。

信号标识符必须能够区分不同卫星和不同频率。系统会忽略同一历元内重复的信号。本后端不会自行构建高度角/CN0 模型，也不会进行星历传播；质量标志与标准差应由上游模块提供。

## 模型与局限性

位姿图中的位姿仍然使用 `Pose2`。`PlanarDopplerFactor` 将每个位姿扩展为 `Pose3`，并将 z、roll（横滚角）和 pitch（俯仰角）固定为零，然后调用 **`gtsam::DopplerFactorArm`**，最后将其雅可比矩阵映射回 `Pose2`。卫星几何信息采用 ECEF 坐标系，速度采用 `map` 坐标系。对每个因子而言，角速度和杆臂都是以车体坐标系表示的常量。

接收机钟差变量以米为单位，用 `c*b` 表示；适配器内部将其转换为秒，并相应地缩放雅可比矩阵。每个时间分段中，第一个成功匹配的历元用于锚定钟差状态；从第二个历元开始，利用实际且为正的历元时间间隔构建因子。时间上出现较大间断时，会开启新的分段。

每个被接受的历元都有一个 `Vector3` 速度变量，并添加一个软约束因子，约束车轮前向速度、侧向速度为零和竖直速度为零。这样就显式建立了姿态与速度之间的耦合关系。该模型假定机器人在平面上无侧滑运动。

车轮信息也会影响前端：默认使用较宽松的速度标准差，以减轻重复使用同一信息（double counting）的影响，但这并不是对交叉相关性的严格处理。应根据实际车轮打滑情况和前端算法调整这些标准差。完整的车轮/IMU 联合模型属于后续工作。

**仅使用多普勒观测时，能够观测的是天线速度与钟差变化。** 如果速度变量不受约束，它可以吸收姿态变化带来的影响。当 `omega x lever_arm == 0` 时，官方因子对姿态的直接雅可比项为零；对于平面偏航，如果杆臂仅沿竖直方向，其直接姿态雅可比项同样为零。

即使杆臂为零，机器人运动时的车轮/无侧滑约束仍有可能提供间接的航向信息。卫星数量多不一定意味着几何条件良好。本方案不宣称多普勒观测能够独立观测姿态，也不宣称能够实现完整的三维姿态可观测性。第一个位姿上设置了较弱的偏航角先验（3.14 rad），使 GNSS 能够帮助对齐地图航向；`map` 到 ECEF 的旋转本身是固定值，不参与联合估计。

当 IMU 和车轮采样数据在目标时刻两侧均有可用样本时，采用插值；对于数据边界，允许在 `sensor_sync_tolerance_s` 范围内使用最近邻样本。GNSS 历元在 `pose_sync_tolerance_s` 范围内关联到时间最近、仍保留的激光扫描节点。这是一种有限时间误差下的近似关联，**不是**对连续轨迹进行插值。应根据机器人运动特性和各传感器采样频率设置容差。

系统至少需要四个有效且彼此不同的信号，并要求视线方向（LOS）/接收机钟差几何矩阵满秩（相对 QR 阈值为 `1e-3`）。无效或缺失的数据不会生成缺乏约束的速度状态或钟差状态。延迟到达或乱序到达的历元会在下一次求解时排序并重新构建。ROS 时钟重置后，必须重置建图器或重启节点；不能把跨越时间跳变的多个会话混合处理。

批量优化会在回环修正时运行，也会周期性运行（默认每 1 s 一次）。自定义节点在建图器互斥锁保护下调用 Karto 的 `CorrectPoses`，并更新现有的 `map -> odom` 变换。地图发布仍遵循前端正常的更新周期。`/gnss_corrected_pose` 发布修正后的位姿，但不会虚构后验协方差。日志会报告原始边数量、多普勒因子数量、参与优化的历元数量、总误差以及原始多普勒均方根误差（RMS）。

原始 GNSS 历史数据量受 `max_epochs` 限制；传感器缓冲区最多保留 20000 个样本。对于已成功匹配的历元，系统会缓存其同步后的观测，因此后续传感器缓冲区淘汰旧数据时，不会导致这些因子消失。

这是一个**批量优化原型**，而不是固定时滞边缘化方案：较早的 GNSS 信息可能会从图中移除。原始 Karto 约束边仍会保留。地图规模增大时，批量求解可能变慢。Karto 序列化只保留其原有位姿图，不保存 GNSS 原始数据；加载地图后，必须重新回放对应观测才能重建 GNSS 约束。

`Clear()` 只清除位姿修正；`Reset()` 会清除位姿图和传感器缓冲区。
